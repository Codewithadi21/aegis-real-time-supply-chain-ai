01 / The challenge

Data can be technically correct—and meaningfully wrong.

Imagine an ML model built around customer purchases. An upstream team quietly changes the meaning of an existing feature to logins, without changing its name or type. The pipeline still reports success.

Before · trusted
◉

Engagement means purchases

The model was trained on a known business definition. The feature engagement_events_30d represents purchase activity.

✓ Valid schema · ✓ Valid meaning

After · silent drift
◇

Engagement now means logins

The column name and integer type remain unchanged, but values now represent a different business event.

✓ Valid schema · ✕ Wrong meaning

The core insight: “Pipeline succeeded” does not mean “the model can trust its features.”

06 / The project story

From a silent data failure to measurable ML impact.

A two-part case study: first, the business challenge and outcome; second, the engineering decisions, verification approach, and lessons from building the prototype.

01 · Challenge & impact ↘02 · Engineering & lessons ↘
01
The challenge & outcome

The reason DataPulse exists.

01 / THE PROBLEM

What did we solve?

An upstream producer changes engagement_events_30d from a count of purchases into a count of logins. The field name and numeric data type stay the same, so conventional schema checks continue to pass—even though an existing churn model is now reading a different business signal.

02 / BUSINESS RELEVANCE

Why would a company care?

A data pipeline can be available and technically healthy while downstream analytics or ML decisions become unreliable. DataPulse demonstrates how to surface that hidden gap and give teams evidence before deciding whether a feature refresh or model-dependent process needs review.

03 / SOLUTION STACK

What did we build it with?

Python, Pandas, NumPy, scikit-learn, SQL, Google BigQuery and Pub/Sub. The workflow combines data contracts, PSI/KS drift checks, a fixed-model paired replay, structured incident reports, and a one-shot cloud event path. GitHub Actions tests the reproducible core.

04 / MEASURED EVIDENCE

What did it achieve?

Across 1,500 held-out synthetic customers, 340 predictions flipped (22.67%). ROC-AUC changed from 0.8157 to 0.5414; false negatives increased from 238 to 458. 25 automated tests passed in the saved Colab run. These are experimental results, not measured company losses.

THE TAKEAWAY

Data quality is more than valid columns: it includes protecting the business meaning of features that drive decisions.

02
The engineering & lessons

How we proved the failure mode.

01 / DESIGN CHOICES

How was the architecture designed?

Generate trusted and changed feature snapshots; validate technical and semantic contracts; compare distributions; replay both inputs against the same churn model and held-out customer IDs; aggregate prediction changes and labeled metrics; then produce a deterministic incident report. BigQuery stores analysis tables, and Pub/Sub transports one synthetic incident into incident history.

02 / CONTROLLED REPLAY

Why use a fixed-model replay?

Retraining a model or changing the evaluation cohort would introduce other explanations for prediction differences. Holding the model and customer IDs constant isolates the comparison to the changed feature snapshot. It shows model sensitivity under controlled conditions—not proof of a causal business loss.

03 / DRIFT DETECTION

How did we detect semantic drift?

Technical checks assessed structure, types, completeness and IDs. PSI and KS revealed distribution differences, but statistics alone could not prove the field's business meaning changed. An explicitly documented semantic expectation and an independent synthetic purchases count provided the additional signal that distinguished logins from purchases.

04 / RESULT VALIDATION

How did we validate the outcome?

Seeded reproducible data, paired customer-level before/after predictions, observed labels, AUC and false negatives, contract checks, incident JSON, and the saved Colab result of 25 passing tests. BigQuery queries and Pub/Sub acknowledgement provide an additional cloud verification path; the project author completed those cloud steps, while the private console outputs are not publicly embedded.

Implementation challenges & what they taught us

01
Colab dependencies and project configuration

Missing Pub/Sub packages and an unchanged placeholder assertion interrupted initial execution. Explicit package setup, proper authentication and consistent PROJECT_ID configuration made the notebook reproducible.

02
Gemini API billing did not match GCP trial availability

The optional Gemini Developer API returned a payment-related error even when cloud trial credits were available. The project therefore kept investigation metrics deterministic and made LLM explanations optional rather than blocking the core pipeline.

03
Publishing is not the same as consuming

An initial Pub/Sub demonstration only published metadata. A subscription, validated consumer, BigQuery incident-history write and post-write acknowledgement were added to demonstrate a complete one-shot path.

04
Portfolio deployment had its own failure mode

GitHub Pages initially returned 404 because Pages had not been configured for Actions. Enabling Pages and successfully running the deployment workflow solved the website-hosting issue; it was separate from the DataPulse pipeline.

ENGINEERING LESSON

Reproducible evidence beats an attractive alert. First prove what changed, then quantify decision impact, preserve an audit trail, and keep potentially disruptive remediation under human review.
